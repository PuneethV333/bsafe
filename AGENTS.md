# AGENTS.md — bsafe (Silent SOS Emergency Web App)

bsafe is a web-based silent emergency alert system: a user in danger triggers a silent SOS (single tap / long-press, zero sound or visible confirmation on-device), which shares their live location with pre-configured trusted contacts and tracks the alert until resolved.

This file is both the build plan and the working agreement for coding agents. Follow it phase by phase — do not skip ahead, merge phases, or leave a phase uncommitted.

## Tooling quirks (learned the hard way)

- **npm 11 blocks lifecycle scripts.** After a fresh `npm install`, run `npm install-scripts approve esbuild prisma @prisma/engines @firebase/util protobufjs` or Prisma engines/esbuild silently break.
- **Prisma 7 uses `prisma.config.ts`** (`import "dotenv/config"` + `defineConfig`), holds `datasource.url`, and the schema has **no `url` field**. The `prisma-client` generator emits to `src/generated/prisma` (gitignored; regenerated by `postinstall`/`prisma:generate`) and the runtime requires the **driver adapter** `@prisma/adapter-pg` (`new PrismaClient({ adapter: new PrismaPg({ connectionString: process.env.DATABASE_URL }) })`).
- Keep the generated Prisma client under `src/` — if it lives outside, `tsc` widens `rootDir` and `nest build` emits to `dist/src/main.js` instead of `dist/main.js`.
- API uses a global `/api` prefix; Vite dev server proxies `/api` → `localhost:3000` **and** `/socket.io` (ws: true) → `localhost:3000` for the realtime baseline.
- **Postgres 18 container:** the official image now wants the data volume mounted at `/var/lib/postgresql` (not `/var/lib/postgresql/data`) — mounting the old path makes the container exit(1).

## Working agreement

- Build one phase at a time, in order. Do not start Phase N+1 until Phase N is committed.
- Before starting a phase, add a short `PHASE_LOG.md` entry; update it again when the phase ships.
- After each phase: build + lint must pass, acceptance criteria met (verify manually), **then commit**.
- Commit message format:
  ```
  phase(N): <short summary>

  - <what was implemented>
  - <what was tested>
  - <known gaps / TODOs for next phase>
  ```
  Split oversized phases into `phase(5a)`/`phase(5b)` instead of merging adjacent phases.
- Never commit secrets (Firebase, Twilio, SendGrid, DB credentials). Use `.env` (already gitignored) + `.env.example` from Phase 0 on.
- **No automated test suites in this build** — explicitly out of scope. Verify acceptance criteria manually.
- "Silent" is a hard UX constraint from Phase 5: no sound, no modal, no visible success animation on the trigger screen.
- Monorepo: use **npm workspaces** — an npm lockfile already exists; do not switch to pnpm/yarn/Nx.
- From Phase 3 on, every controller route must declare its own `@Throttle()` override; never leave a route on the bare global default. Exact limits: `BACKEND_FILES_AND_ROUTES.md` §3.

## Phases

### Phase 0 — Repo & Environment Setup

- **Done (verified 2026-08-13).** npm workspaces, `apps/web` (Vite/React/Tailwind v4/react-query), `apps/api` (NestJS 11 + Prisma 7 + Redis), `packages/shared-types`, `docker-compose.yml`, ESLint + Prettier, `.env.example` for both apps. Acceptance met: `docker-compose up` starts Postgres; `npm run dev` starts both apps (hello + `/api/health`).
- **Commit.**

### Phase 1 — Database Schema & ORM

- Use **Prisma 7** (chosen in Phase 0; schema + models already exist in `prisma/schema.prisma`).
- Write migrations (not manual SQL) for: `users`, `emergency_contacts`, `alerts` (status `sent|acknowledged|resolved`, timestamps, `last_location_id`), `alert_locations` (continuous location history, not a single point), `activity_logs`.
- Seed script with sample data.
- **Acceptance:** migrations run clean on a fresh DB; ER diagram in `/docs` (update `docs/er-diagram.png`).
- **Commit.**

### Phase 2 — Authentication (Firebase)

- Firebase Auth SDK on frontend; NestJS guard verifying Firebase ID tokens (Admin SDK).
- On first login, backend creates/links a `users` row via `firebase_uid`.
- Logout, session persistence, route protection on frontend.
- **Acceptance:** sign up → log in → protected `/me` → log out.
- **Commit.**

### Phase 3 — Redis, Caching & Rate Limiting

- `RedisModule` in `apps/api`; global `@nestjs/throttler` with `nestjs-throttler-storage-redis`.
- Named per-route `@Throttle()` overrides from Phase 4 onward (limits in `BACKEND_FILES_AND_ROUTES.md` §3) — none on bare defaults.
- `CacheService` wrapper (user profile, contacts list; 30–60s TTL; explicit invalidation on writes). BullMQ + Redis as the Phase 6 notification queue.
- **Acceptance:** past-limit requests return 429; contacts served from cache within TTL and invalidated after POST/PATCH/DELETE.
- **Commit.**

### Phase 4 — User Profile & Emergency Contacts

- CRUD `GET/POST/PATCH/DELETE /contacts`, `GET/PATCH /me`.
- Profile + contacts management UI (max 5 contacts, phone/email format, duplicate prevention). SOS disabled until ≥1 contact exists.
- **Acceptance:** full contact management; UI blocks SOS access with zero contacts.
- **Commit.**

### Phase 5 — Core SOS Trigger + Live Location

- Silent trigger UI: one-click **and** long-press variants (configurable); zero audible/visible confirmation on success — only a subtle, ambiguous state (e.g. icon dims).
- Request geolocation permission during onboarding, not at crisis moment. On trigger: create `alert`, start `watchPosition` loop, push updates via WebSocket (REST fallback) + persist to `alert_locations`. Define update interval (10–15s) and degraded cases (permission denied, GPS unavailable, backgrounded tab → last-known location + timestamp to contacts).
- **Acceptance:** trigger creates an alert and streams location updates until resolved.
- **Commit.**

### Phase 6 — Notifications

- Twilio (SMS) + SendGrid/Nodemailer (email) dispatched via BullMQ queue — never synchronously from the request thread.
- On alert creation, enqueue a notify job per contact: user name, alert time, view-only tokenized tracking link (expires when resolved).
- Per-contact, per-channel delivery status (queued/sent/failed — "sent" ≠ "delivered"); exponential-backoff retries with max attempts.
- **Acceptance:** triggering sends real SMS/email in staging; delivery status visible in DB.
- **Commit.**

### Phase 7 — Alert Status Tracking & Contact View

- Public tokenized `/track/:token` page: live map, alert status, timestamps.
- Contacts can acknowledge; user (or contact, per access-control decision) can resolve. `activity_logs` populated on every transition.
- **Acceptance:** contact opens link, sees near-real-time location, acknowledges; user resolves from their device.
- **Commit.**

### Phase 8 — Admin/Monitoring Dashboard (optional scope)

- Authenticated admin view: active/past alerts, response times, filters; read-only reporting (alerts/day, avg ack/resolution time).
- **Acceptance:** admin sees a table of alerts with status and key timestamps.
- **Commit.**

### Phase 9 — Non-Functional Hardening

- Mobile-responsive pass on all screens (SOS trigger + tracking view especially).
- Audit every route has its own `@Throttle()` (none on bare defaults) and Redis-backed limits behave under repeated hits.
- Input validation/sanitization audit (class-validator).
- Load check on location-update path; confirm <2s alert-dispatch latency. Verify manually — no automated tests.
- **Acceptance:** manual full SOS trigger → notify → resolve walkthrough; documented latency numbers.
- **Commit.**

### Phase 10 — Deployment

- Deploy web (Vercel/Netlify), api (Render/AWS/Fly.io), managed Postgres + Redis; production env vars/secrets.
- Basic uptime monitoring/logging (Sentry or health-check endpoint + external pinger). Deployment runbook → `docs/deployment.md`.
- **Acceptance:** production URL live; full SOS flow works end-to-end against production services.
- **Commit.**

### Phase 11 — Documentation Handoff

- Finalize README (setup, architecture diagram, env vars, scripts) and PRD-style summary in `/docs`.
- **Acceptance:** a new developer can clone, follow the README, and run the app locally without questions.
- **Commit.**
